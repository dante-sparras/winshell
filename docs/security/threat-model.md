# Threat model

This records the security boundaries reviewed for 1.0, starting from v0.6.0 (`4689259`). It describes implemented controls and their limits, not a claim that a configuration or diagnostic file is safe to share. Vulnerabilities follow the [private reporting policy](https://github.com/dante-sparras/winshell/blob/main/.github/SECURITY.md).

## Assets, actors and authority

Protect the integrity of installed binaries, the user's files and sign-in entry, the availability of the shell, and private content in logs, reports, notifications, network/device names and captured pixels. Windows owns credentials, consent and the secure lock desktop ([ADR-0008](../adr/0008-windows-owns-the-lock-screen.md)).

Relevant inputs are downloaded release metadata/archives, hand-edited TOML, configuration files, other programs' Windows messages/media metadata, and local CLI/IPC clients. HTTPS protects release transport; it does not make content from a compromised release account/build trustworthy. Malformed local input, a process already running as this user, and a different Windows user reaching the control pipe have different authority.

**A QML configuration is trusted executable code.** It can start programs, read/write files and request network content with the invoking user's authority. Jint's reflection restrictions and recursion limit are not a sandbox, execution-time limit or permission system. Do not treat a downloaded configuration like passive TOML. QML and JavaScript load only from the folder `shell.qml` is in: an import, `Qt.createComponent` or `Loader` path outside it, including a UNC path, is refused before it is read, so a folder that looks self-contained does not pull code from a share. The check compares full paths and follows links inside the folder; it does not limit what the code itself reads or runs. Winshell does not load a configuration whose `shell.qml` has a `Zone.Identifier` stream for the Internet or Restricted zone; it shows the configuration error notice, and doctor fails its config check without reading the files, until the user unblocks the file. Only `shell.qml` is checked, and a download tool that writes no zone, such as `git clone`, is not caught. The runtime, installer and updater do not request elevation; an explicitly elevated launch gives configuration code that token too. Doctor warns about elevated instances. This is a per-user shell, not an elevation broker or a security boundary against code already running with the same authority.

## Boundaries and controls

| Boundary | Implemented control and evidence | Residual risk |
| --- | --- | --- |
| GitHub to portable updater | `Updater` fetches release metadata over HTTPS, requires an HTTPS asset URL and a SHA-256 digest, hashes the download before extraction, and relies on .NET zip extraction to reject traversal. The zip and that digest are kept beside the updates folder. `UpdatesTests` covers wrong/missing digests, architecture selection and failed downloads. Source builds and MSIX do not self-update. | The digest comes from the same release authority as the binary, so it catches corruption, not a compromised release; apply's signature check (next row) is the independent check, and only for a signed Winshell. Download/extracted size is not bounded by Winshell. |
| Staged update to executable folder | Apply runs before a shell starts, with instance checks and a mutex in the host. It opens the saved zip once, denying writers, hashes it, and extracts from that same handle, then copies the extract, so a file swapped in the version folder or the zip is not what gets installed. A mismatch or a missing digest deletes the staged tree and does not copy. When the installed `winshell.exe` has a valid Authenticode signature, every binary SignPath signs (`packaging/signpath/`) that the update has must be validly signed by a certificate with the same subject, checked with `WinVerifyTrust`; otherwise the staged tree is deleted and nothing is copied, so a signed Winshell cannot be replaced by an unsigned one or another signer's. An elevated Winshell installs no update and leaves it for a normal start. Links are not followed. Replaced files move aside and failed copies attempt rollback. `UpdatesTests` and `UpdateRestartTests` exercise staging, rollback, restart and concurrent starts, and signed, unsigned and other-signer updates through a signer seam. | A same-user process can still rewrite both the zip and the digest before apply opens them, or the extract before it is copied. An unsigned Winshell, such as v0.6.x, checks no signature, and logs that it does not. The signature check skips revocation and fetches nothing, so it works offline but accepts a revoked certificate; it matches the subject, not the certificate's key or issuer; and it covers only the binaries SignPath signs, so the runtime and library files in an update are trusted on the digest alone. No signed update was installed: the tests fake the signer, and the real check is only run against an unsigned file, a tampered copy and a Microsoft-signed runtime file. The elevated refusal is covered by a test that passes the elevation in; no elevated process was launched. Cleanup is recursive. Rollback cannot guarantee recovery if Windows also refuses restoring a file. |
| Release to PowerShell installer | `install.ps1` accepts the official HTTPS release base (plus a loopback test override), selects a version/architecture, validates SHA256SUMS, and verifies the zip before replacing the install. Extraction rejects empty/dot/parent/colon path segments and checks the full destination prefix. Install uses a unique temp folder, checks root/bin links, refuses replacement while its binaries run, and attempts rollback. | The script itself and checksums share the release's HTTPS/account trust; `irm | iex` executes that script before any package hash check. The loopback override is not an authenticity guarantee. Parent-link races and an attacker already controlling the user's folders are not isolated. A successful binary install can precede a later shortcut/PATH failure. |
| Installer/uninstaller to user state | Only the per-user install, user PATH, shortcut and opt-in sign-in entry are changed. Uninstall validates the fixed install-root suffix, refuses a linked root and running install, removes matching PATH entries and checks shortcut/sign-in targets. Config/data folders remain. Separate Pester suites use fake profiles and verify the real profile is unchanged, on PowerShell 7 and 5.1 in CI. | Target matching and lexical path checks are not a filesystem sandbox. No machine install, certificate or UAC operation is implemented. Local Pester execution and a real install/uninstall were not performed in this audit. |
| TOML/data file to runtime | `TomlAdapter` parses TOML as data through Tomlyn, reads declared writable properties, rejects unsafe JavaScript integers and preserves values/files on parse or reread failures. A TOML file larger than 1 MiB is not read. Nesting past 64 levels is not applied: Tomlyn throws at that depth, including on a dotted key, and the conversion of a value into a property stops at 64 containers. There is no separate value-count limit. Syntax-tree writes preserve unknown keys and comments ([ADR-0009](../adr/0009-user-config-files-are-toml.md)). `TomlAdapterTests` and `DataLimitsTests` cover malformed input, typed values, recovery and these limits. | TOML strings are not evaluated as JavaScript by the adapter. FileView can write the path trusted QML chooses; it is not confined to the config folder. JSON and other `FileView` reads stop at 64 MiB, with no separate value or depth limit. The limit tests use small budgets and in-memory text, not a multi-megabyte file. Fuzzing has not been done. |
| Local process to CLI/IPC | The server creates the pipe with `FirstPipeInstance`, the user as owner and a medium mandatory label before it writes the instance record. Later instances inherit that descriptor, two wait at once and a replacement opens before a connected one is served so the name always has an instance, the server stops listening rather than reopen a name it has lost, and a taken name gets a new id. Clients accept only a pipe owned by their user and served by `winshell.exe` or `winshellw.exe` at their integrity or higher. The server answers a client below its own integrity with a refusal and logs it. JSON requests dispatch known operations on the UI loop. Callable QML handlers have declared primitive types and argument-count checks; there is no IPC eval operation. Instance records include process start time to mitigate PID reuse. | Same-user callers at the shell's integrity are trusted to invoke exported handlers, reload or stop the instance. Request lines, connections and signal queues are unbounded; idle/broken clients can retain work. Same-user medium edits of instance metadata remain trusted user-writable state. A low-integrity process was not launched in the tests. |
| Runtime failure to local crash report | Reports are created without overwrite, retain at most 50 recognized reports, leave script log output out and redact known credential shapes. The instance log is redacted the same way as it is written, and a process that fails to start is logged by its program alone. Pruning skips a linked report directory and linked files. `CrashReportSafetyTests` covers secret shapes, retention, concurrent writers and junctions. There is no uploader. | Reports and ordinary logs still contain paths, app names and arbitrary exception text. Redaction is best effort, not anonymization: [#135](https://github.com/dante-sparras/winshell/issues/135) records partial cookie/passphrase masking and omitted host lines. Review files before sharing. The deliberate crash test may create a Windows Error Reporting entry under Windows' own policy. |
| PC/configuration to doctor output | Doctor parses QML without running it, reads `preferences.toml`, `launcher.toml` and `quick-settings.toml` with the TOML parser and does not run them, skips linked/hidden/nested config folders, stops after 500 folders, and names a `.qml` file or a TOML file larger than 1 MiB instead of reading it. Write probes create a unique empty file with delete-on-close. Registry, permission and process checks read state; profile path prefixes are masked. `DoctorTests`, CLI tests and a native smoke (10 passes) cover the normal path. | Nesting past 256 levels is a parse error. TOML nested past 64 levels is named and not loaded. Other programs' names and user-chosen paths/messages may remain identifying. JSON output is diagnostic data, not an anonymized upload format. Windows permissions determine what the caller can inspect. |

## Other Windows-facing inputs

The tray host accepts cross-integrity `WM_COPYDATA` to interoperate with Explorer and validates protocol data (`TrayProtocolTests`/`TrayHostTests`). Nothing identifies which app sent an icon, so the window and callback it names are not trusted: a callback below `WM_USER` is never sent, and an elevated shell clicks no app above medium integrity, so a click reaches no further than Explorer's. Like Explorer's, a click can still reach a window at the shell's level that a lower-integrity app named. The host's private test classes do not prove compatibility with every real tray app or Windows update. Hotkeys are released at teardown; tests use an unused chord and do not inject keyboard input.

Media artwork is written to a process-specific temporary cache. The audit reproduced cleanup following a directory junction and deleting an old file outside that cache, using only test-owned temporary folders ([#172](https://github.com/dante-sparras/winshell/issues/172)). That file-safety fix has its own review gate; local storage trust does not justify recursive deletion through links.

Notification access, Wi-Fi consent and Bluetooth pairing stay with Windows and explicit configuration actions. Notification dismissal, capture export and device control can affect private data or system state, so the default tests use fake actions. Capture keeps the Windows border and content-protection rules; saved PNGs use create-new semantics. A custom configuration can still make additional network connections or write its data elsewhere. See [privacy](../privacy.md), [notifications](../notifications.md), [network](../network.md), [Bluetooth](../bluetooth.md) and [capture](../capture.md).

The build/release chain is another trust boundary: packaging downloads pinned tooling, verifies its hashes, and signing depends on SignPath setup and a human approver. Updater/installer hash checks do not establish that signing is active. See the [code signing policy](../code-signing-policy.md). Changes to that release infrastructure belong to its separate review.

## Verification limits and release review

`pwsh scripts/check.ps1` passed on the audited commit with zero warnings and 930 passing tests. That includes update tests using fake HTTP responses, crash safety tests, TOML tests, doctor and instance isolation. A temporary floating-window configuration verified IPC, file-watch reload, doctor and PID-scoped shutdown. No installed binaries, real taskbar, system settings or machine certificates were changed by the smoke.

This was a source/test audit, not a penetration test or dependency vulnerability certification. It did not exercise a real signed download/update, Store deployment/consent, hostile-size input, cross-user IPC, live radio/device actions or Explorer restarts. The maintainer accepted report-quality/redaction follow-up #135 as `post-1.0`: reports stay local and require review before sharing. Store startup #142 is also deferred for portable 1.0, but must be fixed before the first Store submission. File and TOML parse limits ([#164](https://github.com/dante-sparras/winshell/issues/164)) cap a `FileView` read, including JSON, at 64 MiB, and a TOML file or one QML file in doctor at 1 MiB. TOML nesting stops at 64 levels. IPC resource/lifetime limits ([#165](https://github.com/dante-sparras/winshell/issues/165)) are tracked as `post-1.0` availability hardening. Runtime/security fixes require separate PRs and independent review. Dante approves the release after its remaining gates.
