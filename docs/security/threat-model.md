# Threat model

This records the security boundaries reviewed for 1.0, starting from v0.6.0 (`4689259`). It describes implemented controls and their limits, not a claim that a configuration or diagnostic file is safe to share. Vulnerabilities follow the [private reporting policy](https://github.com/dante-sparras/winshell/blob/main/.github/SECURITY.md).

## Assets, actors and authority

Protect the integrity of installed binaries, the user's files and sign-in entry, the availability of the shell, and private content in logs, reports, notifications, network/device names and captured pixels. Windows owns credentials, consent and the secure lock desktop ([ADR-0008](../adr/0008-windows-owns-the-lock-screen.md)).

Relevant inputs are downloaded release metadata/archives, hand-edited TOML, configuration files, other programs' Windows messages/media metadata, and local CLI/IPC clients. HTTPS protects release transport; it does not make content from a compromised release account/build trustworthy. Malformed local input, a process already running as this user, and a different Windows user reaching the control pipe have different authority.

**A QML configuration is trusted executable code.** It can start programs, read/write files and request network content with the invoking user's authority. Jint's reflection restrictions and recursion limit are not a sandbox, execution-time limit or permission system. Do not treat a downloaded configuration like passive TOML. The runtime, installer and updater do not request elevation; an explicitly elevated launch gives configuration code that token too. Doctor warns about elevated instances. This is a per-user shell, not an elevation broker or a security boundary against code already running with the same authority.

## Boundaries and controls

| Boundary | Implemented control and evidence | Residual risk |
| --- | --- | --- |
| GitHub to portable updater | `Updater` fetches release metadata over HTTPS, requires an HTTPS asset URL and a SHA-256 digest, hashes the download before extraction, and relies on .NET zip extraction to reject traversal. `UpdatesTests` covers wrong/missing digests, architecture selection and failed downloads. Source builds and MSIX do not self-update. | The digest comes from the same release authority as the binary; this is not an independent publisher signature. A compromised release can supply both. Download/extracted size is not bounded by Winshell. The downloaded hash is not rechecked after staging. |
| Staged update to executable folder | Apply runs before a shell starts, with instance checks and a mutex in the host. Replaced files move aside and failed copies attempt rollback. `UpdatesTests` and `UpdateRestartTests` exercise staging, rollback, restart and concurrent starts. | Staging and the writable executable folder are trusted per-user storage. Files/junctions changed there by another process with that user's authority are not authenticated. Cleanup is recursive. Do not run a privileged host over storage writable by a less privileged actor. Rollback cannot guarantee recovery if Windows also refuses restoring a file. |
| Release to PowerShell installer | `install.ps1` accepts the official HTTPS release base (plus a loopback test override), selects a version/architecture, validates SHA256SUMS, and verifies the zip before replacing the install. Extraction rejects empty/dot/parent/colon path segments and checks the full destination prefix. Install uses a unique temp folder, checks root/bin links, refuses replacement while its binaries run, and attempts rollback. | The script itself and checksums share the release's HTTPS/account trust; `irm | iex` executes that script before any package hash check. The loopback override is not an authenticity guarantee. Parent-link races and an attacker already controlling the user's folders are not isolated. A successful binary install can precede a later shortcut/PATH failure. |
| Installer/uninstaller to user state | Only the per-user install, user PATH, shortcut and opt-in sign-in entry are changed. Uninstall validates the fixed install-root suffix, refuses a linked root and running install, removes matching PATH entries and checks shortcut/sign-in targets. Config/data folders remain. Separate Pester suites use fake profiles and verify the real profile is unchanged, on PowerShell 7 and 5.1 in CI. | Target matching and lexical path checks are not a filesystem sandbox. No machine install, certificate or UAC operation is implemented. Local Pester execution and a real install/uninstall were not performed in this audit. |
| TOML/data file to runtime | `TomlAdapter` parses TOML as data through Tomlyn, reads declared writable properties, rejects unsafe JavaScript integers and preserves values/files on parse or reread failures. Syntax-tree writes preserve unknown keys and comments ([ADR-0009](../adr/0009-user-config-files-are-toml.md)). `TomlAdapterTests` covers malformed input, typed values and recovery. | TOML strings are not evaluated as JavaScript by the adapter. FileView can write the path trusted QML chooses; it is not confined to the config folder. Whole-file reads and recursive conversion have no Winshell size/depth budget. Fuzzing and hostile-size/depth probes have not been done. |
| Local process to CLI/IPC | The server pipe uses `PipeOptions.CurrentUserOnly`; JSON requests dispatch known operations on the UI loop. Callable QML handlers have declared primitive types and argument-count checks; there is no IPC eval operation. Instance records include process start time to mitigate PID reuse. Instance isolation tests and a PID-scoped native smoke pass. | Same-user callers are trusted to invoke exported handlers, reload or stop the instance. Request lines, connections and signal queues are unbounded; idle/broken clients can retain work. Instance metadata is trusted user-writable state. No cross-user or mixed-integrity penetration test was performed. |
| Runtime failure to local crash report | Reports are created without overwrite, retain at most 50 recognized reports, leave script log output out and redact known credential shapes. Pruning skips a linked report directory and linked files. `CrashReportSafetyTests` covers secret shapes, retention, concurrent writers and junctions. There is no uploader. | Reports and ordinary logs still contain paths, app names and arbitrary exception text. Redaction is best effort, not anonymization: [#135](https://github.com/dante-sparras/winshell/issues/135) records partial cookie/passphrase masking and omitted host lines. Review files before sharing. The deliberate crash test may create a Windows Error Reporting entry under Windows' own policy. |
| PC/configuration to doctor output | Doctor parses QML without running it, skips linked/hidden/nested config folders and stops after 500 folders. Write probes create a unique empty file with delete-on-close. Registry, permission and process checks read state; profile path prefixes are masked. `DoctorTests`, CLI tests and a native smoke (10 passes) cover the normal path. | The folder bound is not a per-file byte bound. Other programs' names and user-chosen paths/messages may remain identifying. JSON output is diagnostic data, not an anonymized upload format. Windows permissions determine what the caller can inspect. |

## Other Windows-facing inputs

The tray host accepts cross-integrity `WM_COPYDATA` to interoperate with Explorer and validates protocol data (`TrayProtocolTests`/`TrayHostTests`). Its private test classes do not prove compatibility with every real tray app or Windows update. Hotkeys are released at teardown; tests use an unused chord and do not inject keyboard input.

Media artwork is written to a process-specific temporary cache. The audit reproduced cleanup following a directory junction and deleting an old file outside that cache, using only test-owned temporary folders ([#172](https://github.com/dante-sparras/winshell/issues/172)). That file-safety fix has its own review gate; local storage trust does not justify recursive deletion through links.

Notification access, Wi-Fi consent and Bluetooth pairing stay with Windows and explicit configuration actions. Notification dismissal, capture export and device control can affect private data or system state, so the default tests use fake actions. Capture keeps the Windows border and content-protection rules; saved PNGs use create-new semantics. A custom configuration can still make additional network connections or write its data elsewhere. See [privacy](../privacy.md), [notifications](../notifications.md), [network](../network.md), [Bluetooth](../bluetooth.md) and [capture](../capture.md).

The build/release chain is another trust boundary: packaging downloads pinned tooling, verifies its hashes, and signing depends on SignPath setup and a human approver. Updater/installer hash checks do not establish that signing is active. See the [code signing policy](../code-signing-policy.md). Changes to that release infrastructure belong to its separate review.

## Verification limits and release review

`pwsh scripts/check.ps1` passed on the audited commit with zero warnings and 930 passing tests. That includes update tests using fake HTTP responses, crash safety tests, TOML tests, doctor and instance isolation. A temporary floating-window configuration verified IPC, file-watch reload, doctor and PID-scoped shutdown. No installed binaries, real taskbar, system settings or machine certificates were changed by the smoke.

This was a source/test audit, not a penetration test or dependency vulnerability certification. It did not exercise a real signed download/update, Store deployment/consent, hostile-size input, cross-user IPC, live radio/device actions or Explorer restarts. The maintainer accepted report-quality/redaction follow-up #135 as `post-1.0`: reports stay local and require review before sharing. Store startup #142 is also deferred for portable 1.0, but must be fixed before the first Store submission. Parsing limits ([#164](https://github.com/dante-sparras/winshell/issues/164)) and IPC resource/lifetime limits ([#165](https://github.com/dante-sparras/winshell/issues/165)) are tracked as `post-1.0` availability hardening. A repeated full check also exposed the known media-session flake; see the [readiness audit](../1.0-readiness.md). Runtime/security fixes require separate PRs and independent review. Dante approves the release after its remaining gates.
