# Windows Bluetooth

`shell.Bluetooth` is a [BluetoothService](reference/winshell-bluetooth.md#bluetoothservice). `StartMonitoring` enumerates the default Windows Bluetooth adapter and paired classic and LE association endpoints, again every three seconds until `StopMonitoring`. Until it is called, the lists are empty and Windows is not asked. Call it while something on screen shows Bluetooth: enumerating takes about a second. Reading never requests radio-control access, pairs, connects, opens a remote device or GATT handle, or changes a radio. Setting `BluetoothAdapter.Enabled` asks Windows to change that adapter's radio. Setting `Discoverable` or `Pairable` asks Windows to change whether the radio can be found or accepts incoming connections. The service starts monitoring when it is created, and while monitoring is on, state refreshes every three seconds. `StopMonitoring` stops that read and `StartMonitoring` starts it again. `Refresh` requests an earlier read. The default shell stops monitoring until quick settings is open.

Call `StartDiscovery` and `StopDiscovery` from a user's action. `Discovering` is read-only. `Ready` distinguishes the first or unavailable read from a completed enumeration. A completed read can have no adapter. `Error` describes a failed read or discovery request. `OperationFailed` reports discovery failures. Failure to enumerate clears the collections. A later successful read recovers. `DefaultAdapter` and `Adapters` represent the default adapter returned by Windows, rather than promising simultaneous support for multiple radios.

The adapter has a Windows device `Id`, `Name`, MAC `Address`, and read-only `State`: `Unknown`, `Off`, `On`, or `Disabled`. `Enabled` is true only for On. Unknown means Windows did not expose radio state. Winshell does not guess that an enumerated adapter is enabled. Setting `Enabled` uses `Radio.RequestAccessAsync`, then `Radio.SetStateAsync` for each Bluetooth radio that is not already in the requested state. The property stays what this adapter's own radio last reported. If that adapter has no radio, the request fails and no other Bluetooth radio is changed. A refusal sets the adapter's `Error` and raises `OperationFailed`. The property changes only when a later read reports the new state. Setting the value it already has does nothing, and reading the service does not ask for radio control. The first real change can show Windows' consent UI. A packaged app declares the `radios` device capability as well as `bluetooth`.

`Discoverable` is whether [`BluetoothIsDiscoverable`](https://learn.microsoft.com/en-us/windows/win32/api/bluetoothapis/nf-bluetoothapis-bluetoothisdiscoverable) reports a local radio as discoverable. `Pairable` is whether [`BluetoothIsConnectable`](https://learn.microsoft.com/en-us/windows/win32/api/bluetoothapis/nf-bluetoothapis-bluetoothisconnectable) reports a local radio as accepting incoming connections. On Windows that call is incoming connections, so a pairable radio can accept a connection from a device that already knows it, not a pairing request alone. Both calls pass a null radio handle. Windows then checks or changes every local radio, and the property is true when any radio reports it. Winshell shows that result on the default adapter. The calls can block, so each one runs on its own thread, off the UI thread. They do not open a remote device handle. The property stays what the last read reported until a later read reports a new value. Setting the value the last read already reported does nothing. A second change, while one is in flight, does nothing.

Windows requires incoming connections before a radio can become discoverable. Setting `Discoverable` to true while `Pairable` is false turns incoming connections on first, then discovery. Setting `Pairable` to false while `Discoverable` is true turns discovery off first, then incoming connections. If the first call fails, Winshell does not make the second. Turning discovery off leaves incoming connections as they are. Turning incoming connections on leaves discovery as it is. [`BluetoothEnableDiscovery`](https://learn.microsoft.com/en-us/windows/win32/api/bluetoothapis/nf-bluetoothapis-bluetoothenablediscovery) keeps the new discovery state for the life of the calling process. When Winshell exits, Windows returns discovery to the state from before the call. If this app turns the radio off and back on, that discoverability does not remain. Windows has no discoverable or pairable timeout.

`PairedDevices` contains paired devices, including absent ones. `NearbyDevices` contains present unpaired devices found during explicit discovery. Nearby membership is Windows' cached `System.Devices.Aep.IsPresent` report, not a guarantee that a device can be reached. `Devices` contains both sets. Starting discovery requires an On adapter. Adapter removal or an Off or Disabled radio stops discovery. Stopping clears unpaired discovery results. Paired devices remain.

A device exposes its Windows association-endpoint `Id`, `Adapter`, `Name`, `Icon`, `Address`, `Paired`, `Present`, `CanPair`, `Connected`, `State`, `BatteryAvailable` and `Battery`. Endpoints sharing a Windows container, or an address when there is no container, are one device. Identity is retained while that grouping key remains stable. `Unpair` unpairs all paired endpoints in the merged device, stopping and reporting the first failure.

`Icon` is a device-type name, such as `audio-headset`, for a configuration to choose a glyph from. It comes from the association-endpoint enumeration. Winshell does not open a Bluetooth device or a GATT handle to read it. The properties are `System.Devices.Aep.Bluetooth.Cod.Major`, `System.Devices.Aep.Bluetooth.Cod.Minor` and `System.Devices.Aep.Bluetooth.Le.Appearance`. A classic class is preferred when a class and an appearance are both present. A class BlueZ does not name leaves the icon empty and does not fall through to the appearance. An appearance is used only when Windows reports no classic class. The names are the ones BlueZ derives, such as `audio-headset`, `audio-headphones`, `audio-card`, `input-keyboard`, `input-mouse`, `input-gaming`, `input-tablet`, `phone`, `computer`, `printer`, `camera-photo`, `camera-video`, `video-display` and `network-wireless`. Winshell does not invent a name for a class BlueZ has none for. A configuration uses the string to pick its own icon.

Battery is a fraction from 0 to 1, read only from the cached Windows Bluetooth battery device property, and cached for up to 30 seconds. It is available only for connected devices when a container exposes a valid level. Unknown or missing values stay unavailable. Winshell never opens a GATT connection to obtain battery data.

Device actions expose read-only `Busy`, `Operation` (`None`, `Connecting`, `Disconnecting`, `Pairing`, `Unpairing`), `Pairing` and `Error`, plus `OperationFailed`. Overlapping actions on one device are ignored. Connection and pairing properties only change when Windows reports the new state. Pairing uses [basic Windows pairing](https://learn.microsoft.com/en-us/windows/uwp/devices-sensors/pair-devices), including system consent and PIN UI. Winshell never automatically confirms a PIN match or logs PINs. No permission is requested on reading the service.

Windows has no universal connect or disconnect call for every Bluetooth device profile. `Connect` and `Disconnect` support paired audio devices through the documented Bluetooth audio driver [one-shot reconnect](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/ksproperty-oneshot-reconnect) and disconnect requests. Other device types reconnect through Windows once paired. The methods report unsupported or failed requests instead of pretending to connect. They do not select a default audio device or change volume.

The default shell's Bluetooth tile opens Windows Settings. It does not set `Enabled`.

Native tests only read adapter and paired-device state. That read calls `BluetoothIsDiscoverable` and `BluetoothIsConnectable` when an adapter is present. Scanning, pairing, unpairing, connecting, disconnecting, cancellation, radio changes, and changes to `Discoverable` or `Pairable` are exercised with a fake backend. Those tests never call `Radio.SetStateAsync`, `Radio.RequestAccessAsync`, `BluetoothEnableDiscovery` or `BluetoothEnableIncomingConnections`.
